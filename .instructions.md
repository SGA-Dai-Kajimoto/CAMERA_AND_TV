# Copilot Agent Instructions (プロジェクトルール)

- このリポジトリでは、何かを修正・追加・削除するごとに必ず docs/TASKS.md も合わせて修正・反映すること。
- バグ修正を行った場合は、必ず docs/BUGFIX_LOG.md に修正内容・日付・理由を追記すること。
- TASKS.mdやBUGFIX_LOG.mdの内容と実装・ドキュメントの整合性を常に保つこと。
- ルール違反や未反映があれば必ず指摘・修正すること。
- すべての作業・提案・自動化においてこのルールを最優先で徹底すること。
- 新たなAPIの仕様（エンドポイント・必須パラメータ・レスポンス等）が判明したときは、必ず docs/api_spec_summary.md に追記すること。

- 作業内容に応じて以下のドキュメントも更新すること:
  - APIのはまりポイント・教訓が判明したとき→ `docs/learn/imaging_edge_api.md` に追記
  - 実装・修正・動作確認のたび→ `docs/log/YYYY-MM-DD.md` に `Did/Got/Next` 形式で追記
  - ログファイルはその日の日付で作成・追記すること

# English (for LLM)
- Every time you modify, add, or delete anything in this repository, you MUST also update docs/TASKS.md to reflect the change.
- Every time you fix a bug, you MUST also update docs/BUGFIX_LOG.md with the fix details, date, and reason.
- Always keep TASKS.md and BUGFIX_LOG.md in sync with the actual implementation and documentation.
- If there is any inconsistency or missing update, you MUST point it out and fix it.
- Whenever new API specifications are discovered (endpoints, required request body fields, response schema, etc.), you MUST append them to docs/api_spec_summary.md immediately.
- Whenever you discover API pitfalls, lessons learned, or design insights, you MUST append them to docs/learn/imaging_edge_api.md.
- After every implementation, fix, or confirmed behavior, you MUST append a Did/Got/Next entry to docs/log/YYYY-MM-DD.md (using the current date).
- This rule takes precedence over all other instructions for this repository.

# Android アプリ開発（Camera_PoC/）
- `Camera_PoC/` 配下の Android アプリを実装・修正する際は、必ず最初に `android_app_instructions.md` を読むこと。
- 実装すべきファイル・参照すべき設計書・PC版との対応関係がすべてそこに記載されている。

# For Android app development (LLM)
- When implementing or modifying the Android app under `Camera_PoC/`, ALWAYS read `android_app_instructions.md` first.
- It contains the list of files to implement, design documents to reference, and the mapping from the PC GUI to the Android app.

# Git ワークフロー
- タスクの実装・修正を開始する前に、必ず `main` ブランチから新しいブランチを切ること。
- ブランチ名は作業内容が分かるように `feature/` または `fix/` プレフィックスを付けること（例: `feature/camera-poc-build-fix`）。
- 作業完了後は変更をコミットし、リモートにプッシュしてPRを作成すること。
- `main` ブランチへ直接コミット・プッシュしないこと。

# Git workflow (for LLM)
- Before starting any implementation or fix, ALWAYS create a new branch from `main`.
- Use `feature/` or `fix/` prefix for branch names that describe the work (e.g., `feature/camera-poc-build-fix`).
- After completing the work, commit the changes, push to remote, and create a PR.
- NEVER commit or push directly to the `main` branch.
